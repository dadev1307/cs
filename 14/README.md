# indexOf / lastIndexOf (бинарный поиск)

Реализация `indexOf` и `lastIndexOf` через бинарный поиск по **отсортированному** массиву. Для объектов значение для сравнения задаётся колбэком.

Сложность: **O(log n)**. Нативные `Array.prototype.indexOf` / `lastIndexOf` — **O(n)** линейный обход.

## API

```ts
indexOf<T, U>(array: T[], value: U, cb?: (item: T) => U): number
lastIndexOf<T, U>(array: T[], value: U, cb?: (item: T) => U): number
```

- **`array`** — отсортированный по возрастанию (по сравниваемому значению).
- **`value`** — искомое значение.
- **`cb`** — опционально: `(item) => ключ` для поиска по полю объекта.
- Возвращает индекс первого / последнего вхождения или `-1`.

## Запуск

```sh
npm run 14
npm run 14:bench
```

### indexOf / lastIndexOf (блок дубликатов)

На `n = 1_000_000` custom binary держит ~**5.4–5.9M hz** (~0.0002 ms), нативный поиск падает до ~**2–3k hz** (~0.33–0.44 ms) — порядок **в тысячи раз** медленнее, чем бинарный поиск по тому же отсортированному массиву.

## Выводы

1. **Бинарный поиск почти не зависит от размера массива.** Custom `indexOf` / `lastIndexOf` дают стабильно ~6–10M операций в секунду на всех трёх размерностях; среднее время остаётся около **0.0001–0.0002 ms** — это O(log n).

2. **Нативные методы деградируют линейно с ростом n.** При needle на ~75% длины `indexOf` вынужден пройти ~75% элементов; на `1_000_000` это ~**0.5 ms** против ~**0.0002 ms** у бинарного поиска (**~5300×** на уникальных значениях).

3. **Выигрыш растёт с размером массива.** На `1_000` custom быстрее натива примерно в **3–6×**; на `100_000` — в **сотни раз**; на `1_000_000` — в **тысячи раз**.

4. **`lastIndexOf` у натива на тех же данных часто быстрее `indexOf`**, потому что обход идёт с конца, а needle ближе к хвосту. Но на больших n бинарный `lastIndexOf` всё равно на порядки быстрее (на `1M` — ~**2265×** на уникальных, ~**3870×** на блоке дубликатов).

5. **Сценарий с дубликатами не меняет картину для custom-реализации** — та же O(log n). Нативный поиск по-прежнему линейный; на блоке повторяющихся значений разрыв на больших массивах такой же огромный.

6. **Ограничение:** custom-версии применимы только к **уже отсортированным** данным (или к ключу, по которому массив отсортирован). Нативный `indexOf` / `lastIndexOf` работают на любом массиве, но на больших отсортированных списках проигрывают по скорости.

**Практический итог:** если массив отсортирован и нужны первое/последнее вхождение — бинарный `indexOf` / `lastIndexOf` оправданы; на сотнях тысяч и миллионах элементов нативный линейный поиск становится узким местом, а бинарный остаётся «плоским» по времени.
