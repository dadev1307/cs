# ДЗ 8 — Парсинг CSV и сжатие

Разные способы парсинга `anime_dataset.csv` и сравнение алгоритмов сжатия (Brotli vs Gzip).

## Сжатие

Исходный файл `anime_dataset.csv` прогнан через `zlib.createBrotliCompress` (с `BROTLI_MAX_QUALITY`) и `zlib.createGzip` (с `Z_BEST_COMPRESSION`) через `stream.pipeline`.

| Алгоритм | Оригинал | Сжатый   | Экономия |
| -------- | -------- | -------- | -------- |
| Brotli   | 40.43 MB | 5.32 MB  | **86.8%** |
| Gzip     | 40.43 MB | 10.22 MB | 74.7%    |

**Итог:** Brotli сжимает почти в **2 раза лучше** Gzip на текстовом CSV (5.32 MB против 10.22 MB). Разница объясняется использованием в Brotli статического словаря и более эффективного энтропийного кодирования, что особенно выигрышно на повторяющихся текстовых токенах CSV. Плата за это — более медленное сжатие; распаковка сопоставима по скорости с Gzip.

## Бенчмарк парсинга

Запуск: `npx vitest bench 8/parseCSV.bench.ts`.

| Режим                          | hz (ops/sec) | mean, ms   | p99, ms    | RME     |
| ------------------------------ | -----------: | ---------: | ---------: | ------: |
| buffer (sync)                  |       7.1364 |     140.13 |     148.76 |  ±2.61% |
| string (sync)                  |       2.9973 |     333.64 |     353.89 |  ±3.27% |
| buffer stream, chunk 100 байт  |       0.0245 |  40 891.80 |  57 927.78 | ±26.47% |
| buffer stream, chunk 64 KB     |       4.2318 |     236.30 |     245.97 |  ±1.75% |
| buffer stream, chunk 256 KB    |       6.0008 |     166.64 |     171.44 |  ±1.21% |

### Выводы

- **`buffer` (sync)** — самый быстрый режим: ~140 мс на файл, ~7.14 ops/sec. Работа напрямую с байтами через `Uint8Array` и посимвольное сравнение по кодам (`charCodeAt`) даёт минимум накладных расходов на декодирование.
- **`string` (sync)** — в **~2.4× медленнее** буфера (~334 мс). Node заранее декодирует весь файл в UTF-16 строку (`utf-8` → JS string), что само по себе недёшево, плюс доступ по индексу к строке дороже, чем к `Uint8Array`.
- **`buffer stream`, chunk 100 байт** — в **~292× медленнее** буфера (~40.9 с, p99 ~57.9 с, RME ±26%). При таком маленьком `highWaterMark` (100 байт) overhead async-итерации и склейки «хвостов» между чанками полностью убивает производительность.
- **`buffer stream`, chunk 64 KB** — ~236 мс, всего в **~1.7× медленнее** синхронного буфера. Рост `chunkSize` с 100 байт до 64 KB дал ускорение **~173×** (с 40.9 с до 236 мс): количество async-итераций падает пропорционально размеру чанка, и overhead генератора амортизируется.
- **`buffer stream`, chunk 256 KB** — ~167 мс, всего в **~1.19× медленнее** sync-буфера и на **~30% быстрее** 64 KB варианта. Дальнейший рост `chunkSize` даёт убывающую отдачу: упираемся в стоимость самого парсинга и I/O.

### Рекомендации

- Файл помещается в память → `mode: 'buffer'`, `async: false`.
- Нужен стрим (огромный файл, сеть) → `mode: 'buffer'`, `async: true`, `chunkSize` ≥ 64 KB (оптимум по этим замерам — 256 KB, разница с sync-буфером всего ~19%).
- Маленькие `chunkSize` (сотни байт — единицы KB) для стрима брать нельзя: overhead async-итерации доминирует над полезной работой.
- Режим `string` имеет смысл только если API потребителя уже требует строки и декодирование всё равно неизбежно.

## Поточный парсинг CSV против MessagePack

Один и тот же набор данных (27 661 строка) записан в двух форматах:

- `anime_dataset.csv` — исходный CSV.
- `anime_dataset.msgpack` — тот же датасет, где каждая строка сериализована как msgpack-объект `{<header>: <value>, ...}` через `PackrStream` из [`msgpackr`](https://www.npmjs.com/package/msgpackr). Генерация — `npx tsx 8/writeMsgpack.ts`.

Оба парсера стримовые: `fs.createReadStream(path, { highWaterMark: chunkSize })` → парсер → `for await (const row of ...)`. Данные целиком в память не загружаются.

### Размеры

| Формат      | Размер   | Относительно CSV |
| ----------- | -------: | ---------------: |
| CSV         | 40.43 MB | 1.000×           |
| MessagePack | 40.57 MB | 1.003×           |

Размеры практически совпадают. Датасет ≈ полностью состоит из текстовых полей (Name, Synopsis, Genres…), и msgpack обязан хранить каждую строку вместе с её длиной. Накладные расходы на заголовки ключей msgpackr почти полностью нивелирует благодаря «records» — форма объекта (порядок и имена ключей) пишется в файл один раз на повторяющуюся структуру, а сами записи ссылаются на эту форму. Существенный выигрыш по размеру msgpack даёт только тогда, когда часть полей — числа, булевы или `null`; на чистом тексте экономии нет.

### Бенчмарк (vitest bench, `8/parseCSV.bench.ts`)

| Режим                          | hz (ops/sec) | mean, ms | p99, ms | RME     |
| ------------------------------ | -----------: | -------: | ------: | ------: |
| CSV stream, chunk 64 KB        |       3.9524 |   253.01 |  258.89 |  ±1.16% |
| CSV stream, chunk 256 KB       |       5.7556 |   173.74 |  175.77 |  ±0.94% |
| MsgPack stream, chunk 64 KB    |       7.0579 |   141.68 |  179.90 | ±11.44% |
| MsgPack stream, chunk 256 KB   |      14.9089 |    67.07 |   74.86 |  ±4.31% |

### Выводы

- **MessagePack стрим при 256 KB чанке — в ~2.6× быстрее CSV стрима при том же чанке** (67 мс против 174 мс) и в ~3.8× быстрее CSV стрима при 64 KB. На одинаковом объёме байт и одинаковом I/O-бэкенде разница объясняется работой парсеров: CSV требует посимволного стейт-машины (кавычки, экранирование, разделители, перевод строк), UTF-8 декодирования каждой ячейки и ручной склейки «хвостов» между чанками; `UnpackrStream` читает тип+длину, копирует готовый диапазон байт и декодирует строку одним батчем из оптимизированного нативного пути.
- **Увеличение `chunkSize` с 64 KB до 256 KB даёт msgpack ~2.1× ускорение**, CSV — только ~1.46×. Msgpack лучше масштабируется по размеру чанка: меньше async-итераций, меньше перехватов `unpackr.write(chunk)`, больше полезной работы на одну итерацию event loop’а. CSV быстрее упирается в стоимость посимвольного цикла — парсинг уже не I/O-bound.
- **Стабильность**: у msgpack при 64 KB наблюдается высокий RME (±11%), у CSV — стабильные ±1%. Причина — msgpackr при маленьком чанке чаще режет запись на границе и вынужден буферизовать хвост; накладные расходы плавают. При 256 KB хвост встречается реже, RME падает до ±4%.
- **Размер выигрыша не даёт**, но скорость чтения — да: если датасет хранится в контролируемом формате (логи, снапшоты, кэш), перевод CSV → MessagePack уменьшает латентность холодной загрузки в разы при сопоставимом месте на диске.
- **Когда CSV всё ещё уместен**: интероп с внешними системами, человекочитаемость, потоковая генерация «на лету» из другого источника, где msgpack-библиотеки недоступны. Для внутреннего pipeline, где формат выбираете вы — msgpack предпочтительнее.
