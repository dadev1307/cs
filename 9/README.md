# ДЗ 9 — Matrix2D и Vector поверх Uint8Array

Сравнение байтового представления данных с нативными JS-структурами по скорости и памяти.

## Запуск

```bash
npm run 9:bench
```

Бенчи написаны на `vitest bench` (см. `matrix.bench.ts`, `vector.bench.ts`).

---

## Matrix2D (256×256 RGBA, 65 536 пикселей)

Сравниваются три представления одной и той же картинки:

- **Matrix2D** — обёртка над `Uint8Array` длиной `W·H·4` байта
- **JSON flat** — `JSON.stringify` плоского `number[]` длиной `W·H·4`
- **JSON nested** — `JSON.stringify` вложенного `TupleRGBA[][]`

### Размер на диске

| Формат                | raw       | gzip     | brotli   |
| --------------------- | --------- | -------- | -------- |
| Matrix2D (Uint8Array) | 262 144   | 208 874  | 141 576  |
| JSON flat array       | 964 097   | 249 295  | 178 092  |
| JSON nested array     | 1 095 681 | 261 279  | 145 170  |

(Цифры в байтах, печатаются `console.table` при запуске бенча.)

### Скорость (vitest bench, чем больше hz — тем лучше)

#### Сериализация (структура → байты для записи/отправки)

| Бенч                                                | hz             | rme    |
| --------------------------------------------------- | -------------- | ------ |
| Matrix2D → `matrix.bytes` (отдать ссылку)           | 20 484 851.90  | ±0.22% |
| Matrix2D → `Buffer.from(bytes)` (полная копия)      | 10 357.00      | ±3.94% |
| flat `number[]` → `JSON.stringify`                  | 446.45         | ±4.22% |
| nested `TupleRGBA[][]` → `JSON.stringify`           | 274.24         | ±2.48% |

Ссылка на буфер **в 1 978× быстрее копии** и **в 45 884× быстрее `JSON.stringify(flat)`**. Даже честная копия 262 KB через `Buffer.from` — **в 23× быстрее** flat JSON и **в 38× быстрее** nested.

> **Важно про асимметрию.** В первой версии бенча сериализация делала `Buffer.from(matrixBytes)` (копия), а десериализация — `new Matrix2D(W, H, RGBA, bytes)` (просто оборачивает существующий буфер). Из-за этого казалось, что десериализация бесплатная, а сериализация — нет. Это артефакт бенча, а не свойство `Matrix2D`. **Реальная сериализация так же бесплатна**: `fs.writeFileSync(path, matrix.bytes)` и `socket.write(matrix.bytes)` гонят буфер напрямую в syscall без копий. Строка `Matrix2D → matrix.bytes` в таблице выше показывает эту реальную стоимость — ~20 миллионов ops/sec, по сути присваивание ссылки. Копия добавлена в бенч только для честного сравнения с `JSON.stringify`, который всегда производит новую строку.

#### Десериализация (байты → пригодная к доступу структура)

| Бенч                                          | hz             |
| --------------------------------------------- | -------------- |
| `new Matrix2D(W, H, RGBA, bytes)`             | 11 180 120.00  |
| `JSON.parse` flat `number[]`                  | 422.72         |
| `JSON.parse` nested `TupleRGBA[][]`           | 220.06         |

`Matrix2D` **в 26 448 раз быстрее** flat JSON и **в 50 804 раза быстрее** nested. По сути — нулевая работа: конструктор оборачивает существующий буфер, парсить нечего. Симметрично «отдаче ссылки» при сериализации (см. выше) — обе операции на бинарном буфере фактически бесплатны.

#### Сериализация + Brotli (реалистичный «снимок на диск»)

| Бенч                       | hz     | mean (ms) |
| -------------------------- | ------ | --------- |
| `Matrix2D bytes → brotli`  | 0.4668 | 2 142.10  |
| `flat JSON → brotli`       | 0.5840 | 1 712.34  |
| `nested JSON → brotli`     | 0.5802 | 1 723.46  |

Здесь JSON-варианты **в ~1.25× быстрее** на сжатии, потому что Brotli быстро находит длинные повторы в текстовых цифрах, а у бинарного буфера выше энтропия — компрессор работает дольше при меньшем выходе.

### Выводы по Matrix2D

1. **(Де)сериализация бинаря фактически бесплатна** — это не «оптимизация», а свойство представления. Данные уже лежат в виде, пригодном для записи в файл/сокет (`fs.writeFileSync(path, matrix.bytes)`) и для чтения обратно (`new Matrix2D(W, H, RGBA, bytes)`). В обе стороны — присваивание ссылки, ~10–20 миллионов ops/sec. JSON же обязан в обе стороны ходить через парсер/сериализатор.
2. **Не путать «копию» с «сериализацией».** В бенче `Buffer.from(bytes)` показан, чтобы было честное сравнение с `JSON.stringify` (та тоже создаёт независимую строку). Но в реальном пайплайне копия не нужна — буфер пишется/отправляется напрямую.
3. **Сырой размер**: бинарь в 4× компактнее JSON. Это пропорционально расходам трафика на сети и на диске.
4. **После Brotli** разрыв в размере сжимается: бинарь 142 KB, JSON 145–178 KB. Архивированный JSON догоняет бинарь по размеру, но уступает по скорости (де)сериализации в **десятки тысяч раз**.
5. **Сжатие бинарного буфера дороже** по CPU, чем сжатие JSON (~1.25× медленнее), потому что у бинарника выше энтропия — компрессор работает дольше при меньшем выходе. Если есть бюджет на CPU при чтении — JSON+Brotli может быть приемлемым форматом обмена.
6. Для in-memory обработки картинки (canvas, GPU, фильтры) альтернатив `Uint8Array` нет: любой JSON-подход сначала надо распарсить и сложить в типизированный буфер.

## Vector (10 000 RGBA-элементов)

Сравнение со «структурой данных по умолчанию в JS» — массивом объектов `{ red, green, blue, alpha }`.

### Push: добавление 10 000 элементов в пустую коллекцию

| Бенч                                                   | hz        |
| ------------------------------------------------------ | --------- |
| `Vector.push` с `reserve(ITEMS)`, единый Uint8Array    | 2 508.02  |
| `Array.push` объектов (новые объекты на каждой итерации) | 12 923.09 |

Array **в 5.15× быстрее**.

### Get: чтение 10 000 элементов

| Бенч                                          | hz        |
| --------------------------------------------- | --------- |
| `Vector.get` → новый `TupleRGBA` (allocates)  | 18 507.32 |
| `Vector.view().red` — поля без аллокации      | 24 103.65 |
| `Array` объектов: `arr[i].red`                | 67 864.02 |

Array **в 2.82× быстрее**, чем `Vector.view()`. `view()` сокращает разрыв vs `get()` примерно в полтора раза за счёт того, что не аллоцирует массив-кортеж.

> **Откуда аллокация в `Vector.get`.** Сам `Vector.get` ничего не аллоцирует — он только читает байтовый offset из items-таблицы и делегирует вызов в `cursor.get()`. Аллокация возникает уровнем ниже, в `RGBA.get()`:
> ```ts
> get(): TupleRGBA {
>   return [                    // ← каждый вызов создаёт новый Array(4)
>     this.bytes.red,
>     this.bytes.green,
>     this.bytes.blue,
>     this.bytes.alpha,
>   ];
> }
> ```
> Литерал `[r, g, b, a]` — это `new Array(4)` с заполнением четырёх слотов и установкой hidden class. На каждый `get` — один объект-массив в young generation, который потом подметает minor GC. Это не баг, это **контракт интерфейса** `View<TValue, TResult, TInner>`: `get(): TResult` обязан вернуть значение типа `TResult`, а для RGBA `TResult = TupleRGBA`, то есть JS-массив (= heap-объект).
>
> Чтобы избежать этой аллокации, используйте `view()` — он возвращает **тот же** инстанс `RGBAView` (cursor переставляется по offset'у), и поля читаются прямо из буфера без создания промежуточных структур.

### Перезапись 10 000 элементов на месте (давление на GC)

| Бенч                                                              | hz        |
| ----------------------------------------------------------------- | --------- |
| `Vector.view().red = ...` — чистый byte-write, ноль новых объектов | 3 086.67  |
| `Array`: мутация полей существующих объектов                       | 13 661.84 |
| `Array`: **замена** объектов новыми (имитация GC-нагрузки)         | 3 475.85  |

Ключевое наблюдение: как только массив объектов начинает **аллоцировать новые объекты на каждом проходе** (последняя строка), он **просаживается до уровня Vector**. То есть при равных GC-условиях преимущество массива объектов сильно сокращается.

### Стресс на realloc: 10 000 push без `reserve`

| Бенч                                                      | hz       |
| --------------------------------------------------------- | -------- |
| `Vector.push` без `reserve` (форсит `reallocCapacity` → `reallocHeap`) | 47.60   |
| `Array.push` без предразмера (V8 сам растит)              | 2 586.68 |

Array **в 54× быстрее**. Без `reserve` Vector копирует весь буфер и обходит items-таблицу при каждой реаллокации.

### Выводы по Vector

1. **На горячем пути CPU** Array of objects стабильно быстрее: V8 инлайнит доступ по `obj.red`, hidden classes стабильны, объекты в young generation собираются дёшево. У Vector каждое поле — `setUint8/getUint8` через offset, это лишние операции.
2. **`view()` бьёт `get()`** примерно в 1.3× — экономия на отсутствии аллокации tuple. Если нужно прочитать одно поле, всегда предпочитайте `view().red` вместо `get()[0]`.
3. **GC-преимущество Vector реально**, но не на коротких бенчах: как только мы сравниваем «мутация существующих объектов» vs «замена объектов» — разрыв с Vector практически исчезает (3 087 vs 3 476 hz). На длинной дистанции с миллионами обновлений и большим working set Vector даст более ровную задержку, потому что не триггерит major GC паузы.
4. **`reserve` обязателен** при известном N. Разница 47 vs 2 508 hz (54×) — цена недостающего вызова `reserve`.
5. **Когда Vector реально нужен**:
   - SoA-данные для GPU/canvas — нужен непрерывный байтовый буфер для прямой передачи в `ctx.putImageData` / `gl.bufferData`.
   - Долгоживущие процессы с миллионами update-операций — отсутствие GC-пауз.
   - Сериализация на диск/в сеть без преобразований — буфер уже в нужной форме.
   - Compact memory layout — 4 байта на элемент vs ~40+ байт на объект `{ r, g, b, a }` в V8.
6. **Когда массив объектов лучше**: обычная бизнес-логика, чтение/мутация в hot-path небольшого размера, удобство отладки. Тут Array выигрывает по скорости и по DX.

## Итого

- **Matrix2D vs JSON** — однозначная победа байтового представления по всем метрикам, кроме скорости Brotli-сжатия (там JSON быстрее за счёт высокой регулярности текста).
- **Vector vs Array** — компромисс: Array быстрее в синтетических бенчах CPU, Vector выигрывает на памяти, GC-стабильности и совместимости с бинарными API. Реальный выбор зависит от того, доминирует ли у вас CPU или GC pressure.
